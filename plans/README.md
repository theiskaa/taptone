# Taptone implementation plan

Follow [001 — Validate and finish the macOS prototype](001-finish-taptone.md). Work in order and review each phase before advancing. Keep local hardware probes, generated fixtures, logs, screenshots, and binaries out of Git.

[002 — Optional trackpad audio](002-trackpad-audio.md) tracks a separate experiment: rendering the mix through the trackpad, not detecting more taps. The live experiment depends on Phase 2.

Physical test report: feedback was barely noticeable, including with **High** sensitivity, and did not match the music to the tester. High sensitivity changes which accents are detected, not motor strength. The route, Activity counters, and whether accents were consistently late versus missed or extra were not recorded; don’t infer those results.

Phase 1 baseline: the release fixture runner produced identical WAVs, labels, and metrics in two runs. Normal sensitivity detected all 20 kicks at 90/120/150 BPM (p95 onset-to-detection ≈10 ms offline). Normal also produced no cues on the upper-band negative fixture; High produced 16 extra cues. This is a fixture result, not a measured live lag or proof that the detector handles music. On the physical Mac, the tester felt all four taps in the audio-free AppKit test, but said the feedback was not strong enough. This rules out beat detection and capture as causes of the weak sensation in that test; it does not quantify live timing. No private API is in the main app.

An isolated, local-only command-line probe resolved the required symbols. Its source and build script are not part of this repository. In the four-pulse physical comparison, the tester confirmed the firmer private pulses were noticeably stronger than the original AppKit taps. Comfort was not explicitly rated. The probe has a bounded `--live` mode for the 20-kick fixture. No changes to the main app’s output or beat detector. Capture failures now reach consumers before potentially blocking teardown; a fake route-change test verifies that ordering. The Phase 1 probe only measured cleanup callback return; the Phase 2 build also surfaces HAL-reported cleanup errors.

**First physical live run (2026-11-22).** QuickTime Player, `kick-120.wav`, Normal, built-in trackpad; the output route was not explicitly recorded. The tester said it “works real nice.” First PCM report: **89.6 ms** from Start. **17 beat reports and 17 driver-accepted requests**, with **zero** reported stale/rate/cap skips or probe inbox drops. Detector hop → report p95: **17.1 ms**; hop → request p95: **29.4 ms**. Automatic expiry completed; capture shutdown callback returned in **5.3 ms**. These are software measurements, not playback-to-touch latency. The 20-kick file produced 17 reports, but this run cannot place the count gap or say all 17 were felt.

**Controlled replay (2026-11-22).** Same 120 BPM fixture, played from the beginning by `afplay` launched with a two-second delay in a separate job. **20 beat reports and 20 driver-accepted requests** with **500.0 ms** between every reported beat, zero skips and zero probe drops. First PCM report: **2,161.4 ms from Start**, including the intentional playback delay. Hop → report p95: **17.0 ms**; hop → request p95: **22.5 ms**, worst request: **34.9 ms** on the first beat. Automatic shutdown callback: **5.5 ms**. The earlier count shortfall did not reproduce; the cause remains unknown. Keep the detector unchanged.

**Explicit Stop (same test session).** The tester pressed Ctrl-C after four kicks and confirmed the taps stopped. All four reported beats had accepted requests and no reported skips or drops. Shutdown callback returned in **1.7 ms**; the output route and continued playback were not separately stated. Phase 1 qualifies the output path on this Mac, not other apps, routes, or devices.

**Phase 2 implementation.** Request invalidation and queue submission now happen in the same order. Tests cover cancellation during setup and blocked I/O start, a route callback arriving after replacement, a restart from another caller while the old tap is closing, startup without PCM versus silence then loss of PCM, and reverse cleanup of simulated partial resources. The probe now reports HAL cleanup statuses separately from callback timing. A failed cleanup blocks subsequent system Start in the same process; Quit and reopen to retry. Both release builds and signatures verified, and the frozen fixture metrics did not change. Atlas checked Start/Stop and the no-PCM message without granting audio access. A narrow Core Audio binding seam now injects ten setup failure cases into `SystemAudioTap`, including denied access, format/UID read failure, listener registration failure and I/O start failure. The tests assert exact reverse rollback, idempotent stop and successful reprepare with substituted HAL functions; they do not force macOS itself to fail. Add/remove now share one native listener block, avoiding separate Swift-to-Objective-C bridges at those two calls. The test rejects a mismatched listener token and verifies that a listener removal error does not prevent the remaining releases. Both final release signatures verified; 41 automated tests passed (including the parameterized rollback test with ten cases).

**Phase 2 granted replay (2026-11-23).** Rebuilt probe, `afplay`, 20 kicks: **20 beat reports and 20 driver-accepted requests**, exactly **500.0 ms** apart, zero skips and drops. First PCM report **97.9 ms** from command start; hop → report p95 **15.3 ms**, hop → request p95 **19.6 ms**. Automatic expiry returned the capture shutdown callback in **2.4 ms**; HAL reported no cleanup errors. This was not a Ctrl-C run, and the route was not explicitly confirmed. This replay predates the native listener binding change. Manual Stop on the latest build, repeated restart, and speaker/headphone route changes remain to verify.

A phase is accepted only when its code review and verification both pass. Mark missing hardware or permission evidence as blocked, not passed.
